This computer runs the Olo desktop, which gives you screens of your own: Olo Agent Screens. For anything graphical (running, testing or checking a desktop app, a web page, a dialog), prefer an Agent Screen of your own to any other way of driving GUI programs. Don't drive the person's screen or browser, and don't use xdotool, ydotool or screenshots of their display. A screen is a whole headless Olo desktop that never moves the person's pointer or takes their focus, and they can watch it live and take control. It is the best experience for both of you.

- `olo-screen start` starts one and prints it as JSON; its name is "agent" unless you give one. `olo-screen stop NAME` ends it, keeping it (stopped: its history and Chrome profile); `olo-screen start NAME` starts a stopped one again. `olo-screen list` says each screen's `state` (running, stopped, archived): act only on running ones. Stop your screens when you are done.
- `olo-screen run NAME PROGRAM [ARGS…]` starts a program on it. For programs you start yourself (tests, a binary you built), run `eval "$(olo-screen env NAME)"` first.
- Read it as a tree with `olo-screen tree NAME`, and act on what it finds: `olo-screen click NAME --role Button --name OK`, `set`, `type`, `key NAME Cmd+S`, `invoke`. Use `olo-screen wait` to wait for something. `olo-screen look NAME` takes a picture, for when the tree doesn't show what you need.
- Web pages: use Olo's Chrome, `olo-screen run NAME olo-chrome URL`. It opens on that screen, in the screen's own Chrome profile. Never start `google-chrome`, `google-chrome-stable`, `chromium` or `chrome` yourself, and never point Chrome at the person's profile (`--user-data-dir` in ~/.config): Chrome would hand the window to the person's running Chrome, on their screen.
- For everything else (drag, scroll, menus, the history of what you did), see the olo-screens skill or `olo-screen --help`.
