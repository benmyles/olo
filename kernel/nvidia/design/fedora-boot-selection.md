# Selecting the NVIDIA prevention build on mutable Fedora

Proposal for qualification on Fedora 45 with GRUB BLS, a Btrfs root and a separate ext4 /boot. The production mutation guard in apps/nvidia stays in place.

## The boot contract

An ordinary Fedora boot uses its installed RPMs. A prevention boot uses one sealed /usr subvolume for the entire boot, including the Fedora RPM database, the module release, indexed dependencies, NVIDIA firmware and host libraries. The distribution's kmod loads modules by its normal paths. The support boundary is the host's admitted Fedora load paths and libraries. A privileged caller supplying other kernel bytes, or an application supplying private driver libraries, can choose different inputs.

Keep Fedora's normal root, /var and separate /home for the trial desktop. Mark /usr read-only at both the subvolume and mount layers. For the initial profile verify the relevant configuration in the stock /etc, then bind-mount the current /etc read-only for this boot. Existing settings are visible. Package and system-configuration changes take place in ordinary Fedora. An update must be fully staged and a new generation admitted before trying the new stack. This limitation needs to be visible at opt-in. A profile that needs writable system configuration during a trial requires narrower protected inputs and its own qualification.

## Preparing a pair

1. On stock, inventory the active GRUB config and environment, the exact stock BLS ID, kernel and ordered initrds, root/LUKS/boot filesystem identities, fstab, policy, firmware search paths, package closure and module tree. Check there is an accessible stock boot and enough free data and metadata space on both filesystems. A service launching after akmods does not establish transaction completion. Capture a consistent stock Btrfs root snapshot and boot artifacts in an offline maintenance interval with no package or boot writers. Enumerate nested subvolumes and other mounts separately. Record native stock before/after identities. Decline unsupported layouts.
2. Retain an independently bootable stock recovery root and an ordinary stock entry. Build the recovery root from that capture. In its own fstab and BLS entry select its own subvolid, mount it read-only, and omit the person's home and writable boot mounts. Give its limited recovery target private runtime state, for example systemd.volatile=state with a bounded /var. Include required configuration, firmware, userspace and five stock modules in the recovery system. Build an independent stock dracut image with the correct embedded host-only command line. The recovery path must work without the candidate gate, ticket or ordinary kernel files. Boot and check it before arming the trial. The everyday way back is the usual mutable Fedora entry.
3. Build unprivileged against the pinned release, open driver source, Fedora prep and patches 0001–0003. Restrict the build environment, descriptors, resources and outputs. Perform trusted signing separately. For the initial payload produce all five modules together. Strip as appropriate, sign the final ELF, compress as Fedora does, and hash the final artifact as well as its ELF. An alternative payload containing a patched core and four exact, unchanged stock binaries requires an explicit five-file manifest and independent mixed-build qualification.
4. On the same Btrfs filesystem make a genuine /usr subvolume containing the contents of the captured /usr. Use reflinks for regular files and preserve hardlink groups, ACLs, capabilities, xattrs, permissions, symlinks and filesystem labels. An ordinary usr directory inside a root snapshot cannot be mounted with subvolid as a separate /usr. Complete the RPM transaction inside an isolated staging installroot with this /usr and private /etc, /var and /boot. It has no host bus or live host mounts. Install a local, distinctly released kmod-nvidia-K RPM in place of its distro counterpart only in this installroot. It owns the canonical extra/nvidia paths; require the exact kernel and pinned driver package identity. Checkpoint the private RPM database including any SQLite WAL. Verify the candidate RPM database and contents, including firmware and multilib consumers. Never enable an akmod or DNF repository on the live root to make this package win.
5. Run the distribution's depmod for the complete staged K tree in isolation. Independently validate unique providers, paths, dependencies, aliases, symbols, soft and weak deps, builtins and device names through the target libkmod and the full indexes. Check unrelated drivers, kmod policy, machine/ELF ABI, required and imported symbols, namespaces, CRCs where present, options, build IDs and signatures. Ensure the stock recovery and the candidate each have their own complete view. Seal the subvolume and record its FSID, subvolume UUID, numeric ID and immutable content identity.
6. Build a private dracut image for the candidate. Every ordered early archive must be understood. Exclude all five NVIDIA modules and audit explicit loaders, dependencies, command lines and alternative paths to the pending real root. Include Fedora's unlock, root, filesystem and Intel graphics support. A policy file requesting omitted drivers is insufficient evidence. Preserve the Fedora-signed kernel and required early microcode. Secure Boot requires qualification of the entire actual boot and module trust path. For the first unsigned trial accept only an explicitly qualified permissive target; unknown, newly enforced or revoked trust disarms the trial.

## Files and publication

| Object | Placement and access |
| --- | --- |
| Sealed trial /usr and recovery root | Dedicated subvolumes below FS tree ID 5, e.g. olo-nvidia/G/usr and olo-nvidia/G/stock. Private parent root:root 0700. Preserve Fedora's target-path labels and normal modes inside each image. Keep staging separate and 0700. |
| Module payload and indexes | Trial /usr/lib/modules/K/extra/nvidia/NAME.ko.xz, root:root 0644, modules_object_t. Indexes root:root 0644 with final-path policy labels such as modules_dep_t. |
| Boot payload | /boot/olo-nvidia/G/{stock,prevention}/, root-owned, with independent kernel, ordered initrds and manifest. Private artifacts 0600 and directories 0700, target boot_t as determined by policy. Copy kernel bytes as their actual signed image. |
| Boot entries | On this Fedora GRUB, proposed names are ~olo-G-stock.conf and ~olo-G-prevention.conf in the effective /boot/loader/entries directory, with G encoded as lowercase hex. Its blscfg filename comparison sorts a leading tilde early in version order and presents newer entries first. Use unique stable Fedora GRUB IDs, root-owned 0600, final-path boot_t. Prove native stock still wins all normal/default and missing-environment cases. |
| Control | /boot/olo-nvidia/control/state, root:root 0600 in a 0700 directory. Keep desired mode, generation, single-use attempt and its disposition separate from GRUB's saved default. Write a new complete file, fsync, rename, fsync parent. Expose a sanitized status to unprivileged callers. |
| Initrd gate | Package /usr/libexec/olo/olo-nvidia-admit, root:root 0755, with a reviewed final-path context and least-privilege SELinux domain if required. Install the gate and switch-root drop-in only into the trial image. |

Resolve and verify final-target contexts on staged inodes, including directories. Keep private signing keys out of build inputs and published boot artifacts. Outside-root symlinks, nested mounts and Btrfs subvolumes need explicit inclusion or rejection. Space budgets cover pinned extents, snapshot metadata and ext4 free space needed by Fedora's next kernel. Sync new files, directories, Btrfs subvolume transactions and private ext4 images before publishing either .conf from a temporary name. Publish and qualify recovery first. A failure can leave an unreferenced generation for garbage collection. Read back actual boot references after ambiguous writes. Garbage collect only unreferenced, unmounted generations and keep a proven stock recovery.

## Entering and leaving

The prevention BLS entry retains the stock root=, rootflags=subvol=root, LUKS and hardware settings. Preserve the resolved early-image order and Fedora GRUB authorization settings. Point linux and initrd to private paths relative to the boot filesystem. Add the following arguments, substituting verified IDs. Resolve or reject conflicting inherited options, including hibernation resume and dynamic bootloader variables.

    mount.usr=UUID=<root-btrfs-fsid> mount.usrfstype=btrfs mount.usrflags=subvolid=<G-usr-id>,ro olo.nvidia=<G> noresume

Systemd's fstab generator mounts that subvolume on /sysusr/usr, then binds it on /sysroot/usr. Attach admission to the actual switch-root service. Fedora's dracut-pre-pivot.service ignores the exit status of its normal hook.

    # initrd-switch-root.service.d/50-olo-nvidia.conf in the private image
    [Unit]
    Requires=sysroot.mount sysroot-usr.mount
    After=sysroot.mount sysroot-usr.mount
    [Service]
    ExecStartPre=/usr/libexec/olo/olo-nvidia-admit

Run admission in the initrd mount namespace. Read the ordinary stock view through a separate read-only mount after the /usr overmount. Match the target machine, actual running kernel and command line, selected image, Btrfs identifiers and seals, desired state and one-use ticket, current stock RPM header set, actual driver/firmware/library hashes, relevant local /usr changes and external configuration against the authenticated manifest. Check signature policy and key trust, sorted mount graph and absence of earlier NVIDIA modules. Cover default loader configuration, firmware search overrides and all active modprobe.d directories, including /run. Reject an unaccounted provider, writable alternate mount, initrd hook, custom loader or library path. Scope the guarantee to the verified host software stack. Validate the read-only /etc bind and avoid exposing a writable alias. Normal queries can use cached preparation evidence for sealed files. Metadata on mutable files cannot certify identity. Bound and measure checks on the boot path.

The candidate profile suppresses package-write jobs and akmods boot, shutdown and per-kernel services with candidate-only runtime unit masks. A pending Fedora offline update boots stock. Verify rejection of direct RPM/DNF writes before scriptlets and preservation of stock unit enablement. The read-only /usr and RPM database enforce the view for the boot. After the switch, allow Fedora's own coldplug and later lazy loads; qualify the second PCI add event after the initrd originally saw the device. No optional satellite needs to be forced into memory to prove selection.

Consume the attempt durably before allowing the real root to run. Failure or uncertainty prevents the switch to prevention. A bounded return to the already selected normal Fedora default is appropriate when that default and consumption are verified. Otherwise leave a visible recovery path or prompt with the explicit stock entry. Keep any resulting Intel-only or failed-driver boot recorded as failed. A kernel hang can require a physical reset. Never repair a loaded mixture by unloading or inserting another driver.

Try once arms one generation. Initially use explicit GRUB menu selection; confirm manual selection cannot become the saved default. For automation prove Fedora GRUB consumes next_entry before transferring control, with the actual environment device and any indirection, and leaves saved_entry selecting stock. Set and read back only the Olo-owned next choice in an exclusive boot-writer interval. Preserve a pending choice owned by another tool. An invalid environment or failed save must still offer ordinary Fedora. A durable ticket independently prevents repeated exposure if GRUB repeats its choice. A failure before the boot code runs also needs a usable manual/firmware recovery path.

For persistent opt-in, issue the next one-use ticket only on an orderly reboot from a qualified healthy generation with current eligibility. An unexpected reset returns to stock. Require explicit retry after a failed or unconfirmed attempt. Off durably cancels pending and future tickets, then clears only Olo's own next_entry. Current resident modules retire at full reboot. A package or system-configuration update boots mutable Fedora, completes distro RPM/akmods/dracut work and prepares a new pair. Show update and opt-out paths before enabling the mode. Block hibernate, hybrid/kexec or userspace-only transitions between generations until separately qualified.

## Acceptance

Status and status --json report desired mode, stock saved ID and actual next ID, running kernel and /usr mount identity, ticket and boot ID, preparation and recovery evidence, package/userspace/firmware identities, trust and per-module selected path, expected ID, resident ID and initstate. Distinguish absent optional modules, mismatched, going, unknown and failed I/O. Report a pending withdrawal, ineligible next boot, last failure, and the qualification stage independently. Never probe the GPU as part of status.

Use an enforcing Fedora guest with the installed GRUB BLS, encrypted Btrfs root and ext4 boot layout. Use distinct, benign fixture modules that can actually reach live state, then check the real set separately on the target kernel. Test all load paths, configuration semantics, updater and boot ordering, stale or cleared state, RPM and kernel removal, rebuilt initrds, one-shot failure before and after switch-root, and repeated power cuts at every publication and consumption boundary. Check labels and denials, shared data persistence, consistent stock recovery, delayed or cancelled builds and boot latency. Reboot an apparently healthy Intel-only session and verify it never blesses a failed trial. Validate sudo, networking, login, normal use and a real Fedora update via stock before offering an everyday opt-in.

Only patches 0001–0003 proceed to spare matching hardware with deliberate consent and a stock return. Verify actual loaded IDs, Intel display, NVIDIA compute checksums, GCOFF and repeated suspend/resume. Keep late reset/rebind, the display/recovery series and fault injection on their existing qualification gates. Keep the workstation mutation guard until the boot implementation and hardware meet their respective release criteria.
